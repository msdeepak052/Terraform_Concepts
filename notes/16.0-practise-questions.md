# Terraform Practice Questions — Question Bank Only

All 57 scenarios from [16-practice-questions-with-answers.md](16-practice-questions-with-answers.md), stripped down to just the requirement text, organized by the same five sections. Attempt each one yourself — write the `.tf` files, run `terraform plan` — before checking the worked answer and Industry Best-Practice Notes in file 16.

---

## Beginner-Level Scenarios

1. **Provision a Single EC2 Instance** — Launch one EC2 instance in AWS, using variables for AMI ID, instance type, and tags.
2. **Create a VPC with a Public Subnet** — Define a VPC with CIDR block `10.0.0.0/16`; add a public subnet, an internet gateway, and a route table.
3. **Use Input Variables** — Parameterize values like VPC name, CIDR, and subnet CIDR.
4. **Define and Use Output Variables** — Output the instance ID and public IP of the EC2 instance.
5. **Create a Simple Security Group** — Allow SSH (port 22) and HTTP (port 80) from any IP.
6. **Destroy Specific Resources** — Use `terraform destroy -target=aws_instance.example` to destroy the EC2 instance only.
7. **Terraform Formatting and Validation** — Run `terraform fmt`, `terraform validate`, and `terraform plan` as part of the workflow.

## Intermediate-Level Scenarios

1. **Create a Reusable VPC Module** — Build a module for VPC creation; accept variables for CIDR blocks, subnet count, etc.
2. **Deploy EC2 Instances in a Private Subnet with a NAT Gateway** — Create a private subnet and a NAT Gateway in a public subnet; launch EC2 instances with internet access via the NAT.
3. **Use Remote State with S3 and DynamoDB** (and the modern S3-native-locking alternative) — Store Terraform state in S3; use DynamoDB for state locking.
4. **Use Workspaces for Environment Isolation** — Create `dev`, `staging`, and `prod` workspaces; use different `.tfvars` files per workspace.
5. **Conditionally Create Resources** — Use `count` or `for_each` to create a resource only under certain conditions.
6. **Use Data Sources to Reference AMIs** — Use `data "aws_ami"` to fetch the latest Amazon Linux 2 AMI.
7. **Pass Variables Using `terraform.tfvars`** — Organize and load variables from `.tfvars` files.
8. **Define Multiple Security Groups Dynamically** — Use `for_each` with a map to create multiple security groups.
9. **Import Existing Resources** — Use `terraform import` to bring an existing S3 bucket under Terraform management.
10. **Provision Multiple EC2 Instances Using `for_each`** — Launch EC2 instances from a map of instance names and types.

## Advanced-Level Scenarios

1. **Build a Multi-Tier Architecture Using Modules** — Separate modules for frontend, backend, and DB; set up networking between the tiers.
2. **Use Dynamic Blocks for Security Group Rules** — Use `dynamic` blocks to define rules based on a variable list.
3. **Split Configuration into Multiple Files and Environments** — Organize code into folders like `modules/`, `env/dev/`, `env/prod/`.
4. **Terraform CI/CD Integration** (GitHub Actions / GitLab CI) — Create CI pipelines that run `terraform init`, `plan`, and `apply`; secure secrets and manage environments.
5. **Use `locals` and Complex Data Structures** — Simplify code using `locals` with nested maps/lists.
6. **Create and Manage an EKS Cluster** — Provision an EKS cluster; deploy a sample Kubernetes app.
7. **Use a Remote Module from GitHub** — Reference a public module and pass variables to it.
8. **Terraform State Management: Move/Remove Resources** — Use `terraform state mv`, `rm`, and `taint`/`-replace` commands.
9. **Handle Resource Dependencies with `depends_on`** — Manage dependencies explicitly using `depends_on`.
10. **Multiple AWS Profiles/Regions** — Use provider aliasing for deployments across accounts or regions.

## Module-Focused Practice

1. **Module for EC2 with Custom Security Group** — Reusable EC2 module accepting AMI ID, instance type, and custom security group rules; outputs instance ID and public IP.
2. **Nested Module Usage** — A root module uses a `vpc` module and an `ec2` module internally, passing VPC outputs as EC2 inputs.
3. **Parameterize Resource Count in a Module** — Support launching multiple EC2 instances via `count` or `for_each`, from a list/map of instances.
4. **Write a Module for S3 Bucket Creation** — Accept parameters for versioning, lifecycle rules, and bucket policy; output bucket name and ARN.
5. **Module with Conditional Logic** — A variable enables/disables creation of a resource (e.g., NAT Gateway) inside the module.
6. **Module for CloudWatch Alarms** — Create alarms for EC2 CPU utilization; accept threshold and alarm actions as variables.
7. **DRY Modules for Multi-Tier Architecture** — A base network module used by frontend/backend/db modules; deploy all three tiers in separate subnets with isolated security groups.
8. **Use of `locals` in Modules** — Refactor a module to use `locals` for computed values like naming conventions or merged tags.
9. **Output Propagation from Modules** — Capture module outputs in the root module and use them in another module (e.g., VPC's `subnet_id` used by an EC2 module).
10. **Use Public Modules** (Terraform Registry or GitHub) — Integrate a public module (e.g., `terraform-aws-modules/vpc/aws`) and customize its behavior via variables.

## Real-World Industry Scenarios

1. **Launch a Scalable Web Application** — VPC with public/private subnets; an Auto Scaling Group of EC2 instances behind an Application Load Balancer; security groups and target groups.
2. **Deploy a Multi-Tier Architecture** — Web (ALB + EC2), App (EC2), DB (RDS) tiers; private subnets for App/DB; routing, security groups, NAT Gateway.
3. **Set Up Terraform CI/CD in GitHub Actions** — Pipeline running `fmt`, `validate`, `plan`, `apply`; environment secrets; separate staging/production workflows.
4. **Terraform with Remote State in S3 and State Locking in DynamoDB** — Backend block with versioned, encrypted S3 bucket and DynamoDB locking.
5. **Manage IAM Roles and Policies** — IAM roles for EC2, Lambda, and ECS services; inline and managed policies; least-privilege access.
6. **Provision an EKS Cluster with Worker Nodes** — Use `terraform-aws-modules/eks/aws`; configure node groups with scaling; output kubeconfig.
7. **Deploy a Serverless Application Using Lambda and API Gateway** — Lambda functions with IAM roles; API Gateway integration; CloudWatch logging.
8. **Blue/Green Deployment Using Terraform Workspaces** — `dev`/`staging`/`prod` workspaces; deploy different versions of the same infrastructure; automate promotion.
9. **Provision a Multi-Region Disaster Recovery Setup** — Two AWS regions via provider aliasing; sync state and DNS via Route 53 failover routing; `terraform_remote_state` for data sharing.
10. **Infrastructure Tagging Strategy** — Consistent tagging module; auto-apply `Owner`, `Environment`, `CostCenter`; enforce via pre-commit hooks or policy.
11. **Manage Secrets with AWS SSM or Secrets Manager** — Store DB credentials in SSM Parameter Store or Secrets Manager; reference via data sources; pass securely to EC2/Lambda.
12. **Scheduled Auto Start/Stop of EC2 Instances** — Use `aws_instance` with Lambda and CloudWatch rules; schedule expressions to cut costs outside business hours.
13. **Monitor Infrastructure with CloudWatch Dashboards** — Custom metrics and dashboards via Terraform; monitor EC2/RDS/EKS metrics; alarm thresholds.
14. **Use Sentinel or OPA for Policy-as-Code** — Guardrails like "no public S3 buckets" or "tag enforcement"; run policies during CI/CD or `apply`.
15. **Automate SSL Certificate Management** — Provision ACM certificates; DNS validation via Route 53; attach to ALB/CloudFront.
16. **Use Terraform to Provision Azure/AWS Hybrid Infrastructure** — Configure providers for both AWS and Azure; VPC in AWS, VNet in Azure; shared secrets/monitoring across clouds.
17. **Import Legacy Resources to Terraform** — Use `terraform import` to bring existing infrastructure under code; clean up and map state to configuration; validate with `plan`.
18. **Create an Audit-Ready Logging and Monitoring Setup** — Enable AWS Config and CloudTrail via Terraform; stream logs to a central S3 bucket; apply retention/lifecycle policies.
19. **Onboard New Environments with a Single Command** — Parameterize environment creation (dev/qa/uat/prod); modules deploy identical infrastructure per environment; separate state/secrets per environment.
20. **Implement Cost Optimization with Auto Scaling and Spot Instances** — Mixed instance policies in an Auto Scaling Group; balance On-Demand and Spot with fallback strategies; predictive scaling or schedules.
